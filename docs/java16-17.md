# Java 16 – 17: records, patterns, sealed types, and the second LTS

March and September 2021. Java 16 standardises two Amber features that had been
previewing since 14. Java 17 is the LTS release most teams jumped to from 8 or
11 — and the one that finally closed the door on reflective access to JDK
internals.

---

## Java 16 (March 2021)

### Records — standard (JEP 395)

**Code:** [`jdk16/Records`](../src/main/java/com/tomtom/genesis/platform/jdk16/Records.java)

```java
record Point(int x, int y) { }
```

One line generates: private final fields, a canonical constructor, accessors,
`equals`, `hashCode` and `toString`.

**Accessors are named after the component, with no `get` prefix** — `x()`, not
`getX()`. This is deliberate: a record is not a JavaBean. Frameworks that insist
on the bean convention need explicit configuration (Jackson has handled records
natively since 2.12).

**The compact constructor** validates or normalises. There is no parameter list
and no explicit assignment — the compiler assigns the fields from the
(possibly reassigned) parameters after the body runs:

```java
record Range(int from, int to) {
    Range {
        if (from > to) throw new IllegalArgumentException("from > to");
    }
}
```

Reassigning a parameter inside a compact constructor is the idiom for trimming
strings, clamping numbers or copying collections.

**What a record cannot do:** extend a class (every record extends
`java.lang.Record`), be extended (it is implicitly final), declare instance
fields beyond its components, or have setters.

**What it can do:** implement interfaces, declare static and instance members,
override any generated member, be generic, nested or local to a method.

**The trap — shallow immutability:**

```java
record Team(String name, List<String> members) {
    Team {
        members = List.copyOf(members);   // without this line, the record is not immutable
    }
}
```

A record guarantees that the *references* cannot be reassigned. Nothing more.
Defensive copying is your job. Real output from the example:

```
source after mutation = [Ala, Bartek, INTRUDER]
team.members()        = [Ala, Bartek]   <- unaffected, because of List.copyOf
```

**Good fits:** DTOs at an API boundary, value objects (money, coordinates,
ranges), multiple return values, map keys, and the leaves of a sealed hierarchy.
**Poor fits:** JPA entities (they need a no-arg constructor and mutable state),
anything whose identity matters more than its value.

### Pattern matching for `instanceof` — standard (JEP 394)

**Code:** [`jdk16/PatternMatchingForInstanceof`](../src/main/java/com/tomtom/genesis/platform/jdk16/PatternMatchingForInstanceof.java)

```java
if (obj instanceof String s && s.length() > 5) { ... }
```

Test, cast and bind in one step. `s` is a **pattern variable**, effectively
final, and it exists only where the compiler can prove the test succeeded.

**Flow scoping** is unlike any other scoping rule in Java — the scope is
computed from control flow, not from the nearest block:

```java
obj instanceof String s && s.isEmpty()   // legal - && short-circuits
obj instanceof String s || s.isEmpty()   // ERROR - s may not exist

if (!(obj instanceof String s)) return;
// reaching here proves obj is a String, so s is in scope for the rest of the method
```

Where it pays off most is `equals`:

```java
@Override public boolean equals(Object o) {
    return o instanceof Person p && age == p.age && Objects.equals(name, p.name);
}
```

`instanceof` already returns false for null, so the null check disappears too.

### `Stream.toList` and `Stream.mapMulti`

**Code:** [`jdk16/StreamAdditions16`](../src/main/java/com/tomtom/genesis/platform/jdk16/StreamAdditions16.java)

`toList()` is shorter than `collect(Collectors.toList())` and returns an
unmodifiable list — but **it is not a shorthand for `toUnmodifiableList()`**.
The three differ in ways that matter:

| Method | Version | Modifiable | Nulls |
|---|---|---|---|
| `Collectors.toList()` | 8 | contract guarantees nothing (in practice yes) | allowed |
| `Collectors.toUnmodifiableList()` | 10 | no | **NPE** |
| `Stream.toList()` | 16 | no | **allowed** |

Verified output:

```
Stream.toList() with nulls      = [a, null, b]   <- accepted
Collectors.toUnmodifiableList() -> NullPointerException
```

If a stream can yield null and you relied on `toUnmodifiableList` to blow up,
switching to `toList` silently changes behaviour.

`mapMulti` is a lower-allocation alternative to `flatMap`: instead of returning
a stream per element, you push results into a consumer. It needs an explicit
type witness — `.<String>mapMulti(...)` — because the compiler cannot infer the
output type from a consumer parameter. That awkwardness keeps it niche. Reach
for it when you emit zero or one element per input, or when allocating a stream
per element would hurt. Java 24's Gatherers cover the harder cases.

## Java 17 (September 2021) — LTS

### Sealed classes — standard (JEP 409)

**Code:** [`jdk17/SealedTypes`](../src/main/java/com/tomtom/genesis/platform/jdk17/SealedTypes.java)

```java
sealed interface Shape permits Circle, Rectangle, Triangle { }

record Circle(double radius) implements Shape { }
record Rectangle(double width, double height) implements Shape { }
record Triangle(double base, double height) implements Shape { }
```

Before this, "a Shape is exactly one of these three" had no expression in the
language. A public interface let anyone add a fourth; a package-private one was
closed but could not be part of your public API; an enum was closed but each
constant could not carry different data. `sealed` gives you the missing option:
**public to use, closed to extend**.

**Every permitted subtype must choose a modifier** — there is no default:

| Modifier | Meaning |
|---|---|
| `final` | the hierarchy closes here |
| `sealed` | it continues, under a new `permits` clause |
| `non-sealed` | it reopens to anyone |

Records are implicitly final, which is why they pair so naturally with sealed
interfaces.

**Other rules:** permitted subtypes must be in the same module, or — for code on
the classpath — the same package. If all subtypes are in the same source file
the `permits` clause may be omitted. `sealed` and `non-sealed` are contextual
keywords, so existing code with a variable named `sealed` still compiles.
(`non-sealed` is the only hyphenated keyword in the language.)

**The JVM enforces it, not just the compiler.** The permits list lives in a
`PermittedSubclasses` attribute in the class file, checked at class-load time —
so generating a subclass at runtime with ASM or Byte Buddy fails too.

Reflection support:

```java
Shape.class.isSealed()                  // true
Shape.class.getPermittedSubclasses()    // [Circle, Rectangle, Triangle]
```

**The payoff** is exhaustiveness: a switch over a sealed hierarchy needs no
`default`, and adding a fourth permitted type breaks compilation at every place
that must be updated. Note that in Java 17 itself, *pattern matching for switch*
was still a preview — sealed types alone were standard. The combination became
fully usable in Java 21.

### Enhanced pseudo-random number generators (JEP 356)

**Code:** [`jdk17/RandomGenerators`](../src/main/java/com/tomtom/genesis/platform/jdk17/RandomGenerators.java)

Before: four unrelated types — `Random` (a 48-bit LCG from 1995 that does a CAS
on every call), `ThreadLocalRandom`, `SplittableRandom`, `SecureRandom`. Writing
a method that took "some source of randomness" meant accepting `java.util.Random`
and forcing everyone into the slow one.

Now there is an interface:

```java
RandomGenerator gen = RandomGenerator.getDefault();       // L32X64MixRandom
RandomGenerator named = RandomGenerator.of("Xoshiro256PlusPlus");
RandomGeneratorFactory.of("L64X128MixRandom").create(seed);   // reproducible
```

`java.util.Random` now implements it, so legacy code fits in. Available
algorithms on JDK 25, discovered at runtime:

```
L128X1024MixRandom, L128X128MixRandom, L128X256MixRandom, L32X64MixRandom,
L64X1024MixRandom, L64X128MixRandom, L64X128StarStarRandom, L64X256MixRandom,
Random, SecureRandom, SplittableRandom, Xoroshiro128PlusPlus, Xoshiro256PlusPlus
```

The naming scheme: LXM algorithms are `L<a>X<b>Mix`, where `<a>` is the size of
the linear congruential part and `<b>` the xor-shift part.

**Capability interfaces** are the interesting part. `SplittableGenerator.split()`
produces a generator statistically independent of its parent — what you want in
parallel work, instead of sharing one generator and contending on it, or seeding
each thread by hand and hoping the streams do not overlap. `jump()` and `leap()`
skip a fixed distance ahead, giving reproducible per-worker substreams.

**Take `RandomGenerator` as a parameter, not `Random`** — then tests can pass a
fixed-seed generator and production can pass the fast one.

None of these are cryptographically secure. Tokens, passwords, session ids and
nonces come from `SecureRandom`.

### Strongly encapsulate JDK internals (JEP 403)

The end of a six-year migration. `--illegal-access` is **gone** — not flipped
to `deny`, removed. Passing it produces a warning and no effect.

Reflective access to JDK internals now requires explicit, per-package flags:

```bash
--add-opens java.base/java.lang=ALL-UNNAMED
--add-exports java.base/sun.nio.ch=ALL-UNNAMED
```

This is the single biggest source of "it ran on 11 but not on 17" reports.
`sun.misc.Unsafe` remains accessible — it lives in `jdk.unsupported`, which is
open by design.

### The licensing change worth knowing

Oracle JDK 17 reverted to being free for production use, under the new
**No-Fee Terms and Conditions** licence — but only until one year after the
*next* LTS is released. That "free, but with an expiry date" model is why most
organisations standardised on a free OpenJDK build (Temurin, Corretto, Zulu,
Microsoft, Red Hat) rather than Oracle's.
