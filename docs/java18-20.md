# Java 18 – 20: UTF-8, a web server, and virtual threads in preview

March 2022 to March 2023. Three non-LTS releases. Java 18 contains the single
most useful "invisible" change of the decade; 19 and 20 are largely the runway
for Java 21.

---

## Java 18 (March 2022)

### UTF-8 by default (JEP 400)

**Code:** [`jdk18/Utf8ByDefault`](../src/main/java/com/tomtom/genesis/platform/jdk18/Utf8ByDefault.java)

Up to Java 17, APIs that did not take an explicit `Charset` used *the default
charset*, derived from the OS locale:

```
Linux / macOS with LANG=en_US.UTF-8   -> UTF-8
Windows, Polish locale                -> windows-1250
Windows, Japanese locale              -> windows-31j
a container with no LANG set          -> US-ASCII
```

So `new FileReader("data.txt")` read the same file differently on different
machines. That is the mechanism behind the perennial bug report: *"accented
characters are fine locally and broken in the Docker image."* Nothing in the
code differed — only the environment did.

From Java 18, `file.encoding` is UTF-8 everywhere:

```
Charset.defaultCharset()               = UTF-8
System.getProperty("file.encoding")    = UTF-8
System.getProperty("native.encoding")  = UTF-8   <- new in 18
System.getProperty("stdout.encoding")  = UTF-8   <- new in 19
```

**`native.encoding` is the new escape hatch.** It reports what the OS actually
uses, which is what you want when talking to native tools — a process you spawn,
a console, a file produced by another program on the same machine.
`stdout.encoding` and `stderr.encoding` are separate on purpose: a Windows
console may still be cp852 even though files are UTF-8.

**This change can break working systems**, which is why it took until 18. If an
application wrote files with the platform charset on Java 11 and reads them back
on Java 18, the encodings no longer match. Escape hatches, in order of preference:

1. Pass an explicit `Charset` everywhere — the permanent fix.
2. `-Dfile.encoding=COMPAT` — restores the Java 17 behaviour exactly.
3. `-Dfile.encoding=windows-1250` — pins one specific legacy charset.

There is no compiler flag that finds the risky call sites. The practical tool is
a grep for the constructors that take no charset: `FileReader`, `FileWriter`,
`InputStreamReader`, `OutputStreamWriter`, `PrintWriter`, `PrintStream`,
`Formatter`, `Scanner`, `String.getBytes()`, `new String(byte[])`,
`URLEncoder`/`URLDecoder`, `Properties.load(InputStream)`.

**`javac` was not changed by JEP 400** — source files are still read with the
platform charset unless you pass `-encoding UTF-8`. Maven's
`project.build.sourceEncoding` covers that, and this project sets it.

### Simple Web Server (JEP 408)

**Code:** [`jdk18/SimpleWebServerDemo`](../src/main/java/com/tomtom/genesis/platform/jdk18/SimpleWebServerDemo.java)

```bash
jwebserver                  # serves . on localhost:8000
jwebserver -p 9000 -d /srv/files -b 0.0.0.0 -o verbose
```

This replaces the reflex of reaching for `python3 -m http.server`. It ships
inside the JDK, so there is nothing to install — and it makes a convenient
target when you are learning `HttpClient`.

From code:

```java
HttpServer server = SimpleFileServer.createFileServer(
        new InetSocketAddress("localhost", 0), directory, OutputLevel.NONE);
server.start();
```

Deliberate limitations: GET and HEAD only (POST returns 501), HTTP/1.1 only, no
HTTPS, no authentication, binds to loopback by default. The JEP says outright it
is not for production — treat it like `jshell`, a development tool.

`SimpleFileServer.createFileHandler(path)` gives you a handler you can mount on
your own `HttpServer` alongside other routes, which is handy when a test needs
both static files and a stub endpoint.

### Also in 18

| Change | Note |
|---|---|
| **Code snippets in Javadoc** (JEP 413) | `{@snippet ...}` — sample code that the build can actually compile and test, instead of `<pre>` blocks that rot |
| **Internet-Address Resolution SPI** (JEP 418) | Pluggable DNS resolution — needed for virtual threads, since the built-in resolver blocked in native code |
| **Finalization deprecated for removal** (JEP 421) | `finalize()` has been discouraged since the 1990s; now formally on the way out. Use `Cleaner` or try-with-resources |
| **Vector API** (JEP 417) | Third incubator |

Almost entirely previews — but the previews are the ones that matter.

| **Structured concurrency** (JEP 428) | incubator | still preview in 25 |

### The small standard additions

**Code:** [`jdk21/SmallAdditions21`](../src/main/java/com/tomtom/genesis/platform/jdk21/SmallAdditions21.java)
covers these alongside the Java 21 ones.

```java
Thread.sleep(Duration.ofSeconds(2))    // instead of a bare long
future.state()                         // RUNNING | SUCCESS | FAILED | CANCELLED
future.resultNow()                     // never blocks
future.exceptionNow()
```

`Future.state()` fills a real gap: before it, discovering *how* a completed
future finished meant calling `get()` inside a try/catch — and `get()` blocks,
which is not what you want when inspecting a batch of futures that have already
completed.

`ExecutorService` also became `AutoCloseable` in 19, which is why the virtual
thread examples use try-with-resources instead of the
`shutdown`/`awaitTermination`/`shutdownNow` dance.

Also in 19: the **Linux/RISC-V port** (JEP 422).

## Java 20 (March 2023)

The quietest release in the entire six-month era. Every JEP in it is a preview
or incubator repeat:

| Feature | Status in 20 |
|---|---|
| Scoped values (JEP 429) | incubator |
| Record patterns (JEP 432) | second preview |
| Pattern matching for switch (JEP 433) | fourth preview |
| Foreign Function & Memory API (JEP 434) | second preview |
| Virtual threads (JEP 436) | second preview |
| Structured concurrency (JEP 437) | second incubator |
| Vector API (JEP 438) | fifth incubator |

There is nothing here to learn separately. Java 20 exists so that Java 21 could
ship five major features as final on the same day.

Worth noticing as a pattern, though: **virtual threads went through two previews
and pattern matching for switch through four.** The API changed between them.
That is the argument against writing production code against preview features,
however tempting the feature is.
