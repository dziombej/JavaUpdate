# Java 22 – 24: filling in the gaps

March 2024 to March 2025. Three non-LTS releases that finish work started years
earlier: the Foreign Function & Memory API replaces JNI, stream gatherers give
intermediate operations the extension point collectors always had, and the
Class-File API ends the JDK's dependency on a bundled fork of ASM.

---

## Java 22 (March 2024)

### Unnamed variables and patterns (JEP 456)

**Code:** [`jdk22/UnnamedVariables`](../src/main/java/com/tomtom/genesis/platform/jdk22/UnnamedVariables.java)

The underscore becomes a way to say *"there is a value here and I deliberately
do not care about it"*.

A thirteen-year plan, finished:

| Version | `_` |
|---|---|
| up to 8 | an ordinary, legal identifier |
| 8 | using it produces a warning |
| 9 | a compile **error** — the character is reserved |
| 21 | usable in patterns (preview) |
| 22 | standard, for patterns **and** local variables |

```java
var _ = queue.poll();                    // the value is required by the API, not by me
catch (NumberFormatException _) { }      // only the fact matters
for (var _ : list) { count++; }
try (var _ = openScope("request-42")) { } // opened purely for the side effect
```

**The original motivation was patterns.** Without it, deeply nested record
patterns force you to name every component even when one in six is used:

```java
case Line(Point(int x1, int y1), Point(int x2, int y2)) when y1 == y2 ->
case Line(Point(_, int y1), Point(_, int y2)) when y1 == y2 ->
```

`_` alone matches any value of any type, so the component type disappears too:
`case Point _ ->`, `if (obj instanceof Line(var start, _))`.

**Allowed:** local variables, `for` and for-each variables, `catch` parameters,
try-with-resources variables, lambda parameters, type patterns, record pattern
components.
**Not allowed:** fields, method parameters, and reading it back — there is
nothing to read.

The key property: `_` declares no name at all, so it can appear many times in
one scope without clashing. It is not a variable called underscore; it is the
absence of a name.

### Foreign Function & Memory API — standard (JEP 454)

Previewed since 19 (and incubating since 14 under other names). The replacement
for JNI, and the end of `sun.misc.Unsafe` for off-heap memory.

```java
try (Arena arena = Arena.ofConfined()) {
    MemorySegment segment = arena.allocate(1024);          // off-heap, bounds-checked
    segment.set(ValueLayout.JAVA_INT, 0, 42);

    Linker linker = Linker.nativeLinker();
    MethodHandle strlen = linker.downcallHandle(
            linker.defaultLookup().find("strlen").orElseThrow(),
            FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));
}
```

Why it matters even if you never call a C function:

- **No C code to write.** JNI required a `.c` file, a compiler, a build step and
  a platform-specific `.so`/`.dll`. FFM is pure Java.
- **Memory is scoped and bounds-checked.** An `Arena` frees everything it
  allocated when it closes; a use-after-free throws rather than corrupting the
  heap. `Unsafe` offered neither guarantee.
- **`jextract`** generates the Java bindings from a C header file.

This is the foundation under modern native-interop libraries and under the
eventual removal of `sun.misc.Unsafe`'s memory-access methods (deprecated in 23).

Note the runtime guard: calling native code needs `--enable-native-access=ALL-UNNAMED`
or the module name, otherwise you get a warning that will become an error.

## Java 23 (September 2024)

Largely a preview-consolidation release. Two things are worth knowing.

### String Templates were withdrawn

`STR."Hello \{name}"` was previewed in 21 and 22, and then **removed entirely
in 23**. The expert group concluded the design coupled template processing to
string interpolation too tightly and wanted to reconsider.

This is the most useful thing to know about Java 23, because the feature was
heavily blogged about during its preview. Any tutorial showing `STR."..."`
describes something that does not exist in any current release.

It is also the preview mechanism working exactly as designed: a feature that
turned out to be wrong was withdrawn at zero cost to production code, because
`--enable-preview` class files never load anywhere else.

### Markdown in Javadoc (JEP 467)

```java
/// A summary written in Markdown.
///
/// - bullet lists that need no `<ul>`
/// - [links][JavaDoc] and `code spans`
/// - fenced code blocks
```

Triple-slash comments are parsed as CommonMark. Twenty-five years of `<p>`,
`&lt;` and `{@code}` finally optional.

### Also in 23

| Change | Note |

| **Generational ZGC by default** (JEP 474) | The non-generational mode is deprecated; removed in 24 |

## Java 24 (March 2025)

The largest non-LTS release ever — 24 JEPs — because it was the last stop before
the Java 25 LTS.

### Stream gatherers — standard (JEP 485)

**Code:** [`jdk24/StreamGatherers`](../src/main/java/com/tomtom/genesis/platform/jdk24/StreamGatherers.java)

Gatherers are to **intermediate** stream operations what Collectors are to
terminal ones: an extension point. Since Java 8, `Stream` has had a fixed set of
intermediate operations and no way to add one.

**Built-in gatherers:**

```java
stream.gather(Gatherers.windowFixed(3))      // [[1,2,3],[4,5,6],[7]]
stream.gather(Gatherers.windowSliding(3))    // [[1,2,3],[2,3,4],[3,4,5],...]
stream.gather(Gatherers.fold(() -> "", (a, n) -> a + n))   // reduce, as an intermediate step
stream.gather(Gatherers.scan(() -> 0, Integer::sum))       // running total
stream.gather(Gatherers.mapConcurrent(4, this::slowLookup))
```

**`mapConcurrent` has the biggest practical payoff.** It runs the mapping
function on **virtual threads**, at most N at once, and **preserves input order**
in the output. Verified: six lookups of 100 ms each, four at a time, complete in
217 ms.

Use it instead of `stream().parallel()` whenever the work is I/O bound.
`parallel()` uses the common ForkJoinPool, which is sized for CPU work and
shared with the rest of the JVM — blocking in it is a known trap.

**Writing your own.** A gatherer has four parts, in argument order: an
*initializer* creating private mutable state, an *integrator* called per element
that pushes results downstream and returns `false` to stop the stream early, a
*combiner* for parallel streams (omit it to stay sequential), and a *finisher*
to flush anything buffered.

```java
static <T, K> Gatherer<T, ?, T> distinctBy(Function<T, K> key) {
    return Gatherer.ofSequential(
            ArrayList<K>::new,
            (seen, element, downstream) -> {
                K k = key.apply(element);
                if (!seen.contains(k)) { seen.add(k); return downstream.push(element); }
                return true;
            });
}
```

That one is `distinct()` by an arbitrary key — not expressible before, because
`distinct()` only knows `equals`.

**When not to.** If a plain `map` or `filter` would do, or the logic is clearer
as a loop. The interface is dense, and a reader meeting it for the first time
will spend longer on your gatherer than on the loop it replaced.

### Class-File API — standard (JEP 484)

**Code:** [`jdk24/ClassFileApiDemo`](../src/main/java/com/tomtom/genesis/platform/jdk24/ClassFileApiDemo.java)

A JDK-maintained library for reading, writing and transforming `.class` files,
replacing the private fork of ASM the JDK used internally.

The chronic problem it solves: every new class-file version needs a new ASM, and
with a six-month cadence, libraries that generate bytecode break twice a year.
Anyone who upgraded a JDK and met `Unsupported class file major version 65` has
seen it. A library that ships *with* the JDK is never out of date with the format.

Reading:

```java
ClassModel model = ClassFile.of().parse(Files.readAllBytes(path));
model.thisClass().asInternalName();
model.majorVersion();                     // 69 on Java 25; major - 44 = the release
model.methods();                          // immutable tree, not visitor callbacks
```

Generating, and the result actually running:

```java
byte[] bytes = ClassFile.of().build(ClassDesc.of("GeneratedHello"), builder -> builder
        .withMethodBody("greet", MethodTypeDesc.of(CD_String, CD_String),
                ACC_PUBLIC | ACC_STATIC,
                code -> code.ldc("Hello, ").aload(0)
                        .invokevirtual(CD_String, "concat", MethodTypeDesc.of(CD_String, CD_String))
                        .areturn()));
// -> 209 bytes; loaded and invoked: greet("world") = "Hello, world"
```

This is for framework and tool authors — agents, mocking libraries,
instrumentation, build plugins. Application code will never touch it. Worth
knowing anyway for the `major - 44` arithmetic when reading a version error:
65 means Java 21, 69 means Java 25.

### Virtual threads stop pinning on `synchronized` (JEP 491)

The most consequential small change in 24. A virtual thread now unmounts inside
a `synchronized` block, so the main sharp edge of Java 21's virtual threads is
gone. Libraries no longer need to rewrite `synchronized` as `ReentrantLock` to
be virtual-thread friendly. JNI frames still pin.
